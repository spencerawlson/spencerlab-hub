The Great Migration: Aegis production comes home

The API behind two live SaaS products moved from a cloud droplet to a VM on a Proxmox host in this lab. No ports opened, the home IP stayed hidden, and the droplet bill stopped. Getting there meant one surprise on the new box and one outage after it.

Moved 2026-10-13 From DigitalOcean droplet To homelab VM · Cloudflare Tunnel

Background

Three homes in three months

Aegis CloudOps and Fishing Rod Terminal share one backend: a Python API with Postgres and Redis. The frontends are on Vercel and only rewrite /api/* to it. The backend has moved twice:

  • AWS, until early August. It cost about $99 a month for a product with no paying customers yet, so the estate was hibernated.
  • A DigitalOcean droplet, about $24 a month plus backups. It ran the same docker compose stack: Caddy in front, then the API, Postgres and Redis, with no ports published except Caddy's.
  • The homelab, from 2026-10-13. It's a VM on the third Proxmox host, reached the same way this site is: through an outbound Cloudflare Tunnel.

Hosting it here wasn't about the money alone. This site has run behind a tunnel since September (how that started), and the pattern had proved itself. The droplet was the last piece of rented infrastructure in the stack.

Design

The request path

request path
browser → Vercel (aegiscloudops.io / fishingrodterminal.io, rewrites /api/*)
        → api.aegiscloudops.io        # Cloudflare DNS, proxied
        → Cloudflare Tunnel           # cloudflared dials OUT from the VM
        → cloudflared → 127.0.0.1     # loopback only
        → Caddy (security headers) → backend → postgres / redis
  • Nothing is forwarded on the router. A new home IP changes nothing, and the home IP is never published.
  • The tunnel origin is loopback-only. Caddy's tunnel site isn't published to the LAN; only cloudflared on the same box can reach it.
  • DNS moved too. aegiscloudops.io's nameservers moved from the registrar to Cloudflare so the tunnel hostname could live in the same zone. Fishing Rod's domain didn't need to move: its API calls already go through the Aegis hostname.

Part 01 · the cutover

Moving it without losing data

  1. Copied the compose stack and the backend onto the VM. Secrets were copied by hand and never went near git.
  2. Stopped the droplet's backend, dumped its Postgres and restored it on the VM.
  3. Brought the stack up on the VM and checked it on loopback before anything public pointed at it.
  4. Added the tunnel's public hostname and removed the old A record.
  5. Turned the droplet's Caddy into a forwarder to the new home, so clients still holding the old DNS answer kept working.

The droplet's containers were stopped with restart policy no rather than deleted, which leaves a rollback path: restore a dump there, start three containers and put the record back. Deleting the droplet is a separate decision for once the old DNS traffic has died away.

◆ Restore-tested before relying on it

The nightly pg_dump on the new box was restored into a throwaway database on day one (78 tables back) before it counted as a backup. A dump that has never been restored is only a hope.

Part 02 · the surprise

Port 8080 was already taken

The plan put the tunnel origin on port 8080. Something was already listening there. It was a MicroK8s API server from an old experiment, started with --insecure-bind-address=0.0.0.0: an unauthenticated Kubernetes API on every interface of the machine about to hold production data.

✕ What it would have meant

Anyone on the LAN could have talked to that API with no credentials at all. It wasn't reachable from the internet, because nothing on this network is, but "only the LAN" is exactly the assumed-breach position the pentest write-ups start from.

It was removed rather than reconfigured, since nothing used it. The tunnel origin moved to a different port anyway, so the next leftover can't collide with it either.

◆ Lesson

Before moving a service onto a box, list what's already listening on it (ss -tlnp). Reused machines accumulate old experiments, and old experiments were usually built for convenience rather than security.

Part 03 · deploys

From 90 seconds of 503s to none

The first deploy on the new box produced about 90 seconds of public 503s. Caddy checked the backend's health every 30 seconds, so after a restart it kept the upstream marked down long after the API was ready, and it failed every request in the meantime.

Caddyfile
reverse_proxy backend:8000 {
	health_uri /health
	health_interval 5s       # was 30s
	lb_try_duration 30s      # hold a request while the upstream comes back
	lb_try_interval 500ms
}

The next deploy was measured with a probe every 2 seconds: 89 responses, all 200, and one client-side timeout while Caddy held a request. Not one 503.

▲ The reload that silently did nothing

The Caddyfile is a single-file bind mount. Writing a new file and mv-ing it into place leaves the container looking at the old inode, and caddy reload cheerfully reports "config is unchanged". Edit the file in place, or restart the container so it binds the new file.

Part 04 · the outage

25 minutes down, and why it took that long

The same night the internet connection dropped and the host rebooted. The root cause was outside the lab, but the recovery was slower than it needed to be. All six VMs on the host booted at once, and Docker on the production VM took about three minutes to come up while they fought over the disk. Total public outage: about 25 minutes. Nothing alerted on it; it was found by hand.

proxmox host · bash
qm set 101 --startup order=1,up=60   # production first, alone, 60 s head start
qm set 100 --startup order=2         # everything else after it

After a reboot, production now starts first and alone. An external uptime check on the API's /health is next, so the next outage is reported by a monitor rather than noticed by a person.

Part 05 · honesty

The claims the move made false

A migration changes more than where packets go. Three public statements were true on AWS and stopped being true on the night of the move:

  • The Data Handling page said production ran in AWS us-east-1.
  • The landing page and the Security page said data at rest was on encrypted volumes.
  • The security questionnaire sent to prospects said both.

The new disks aren't encrypted at rest. Re-encrypting means rebuilding the VM or its storage, which isn't a change to make unattended, so the claims were corrected instead. The pages now say production runs on company-operated servers in Canada, encrypted in transit, with encryption at rest being re-established. Each questionnaire line is marked verified or gap.

◆ Lesson

Infrastructure changes have a documentation blast radius. When something moves, search the marketing pages, the trust page and every document sent to a customer for what they say about where things run and how they're protected.
