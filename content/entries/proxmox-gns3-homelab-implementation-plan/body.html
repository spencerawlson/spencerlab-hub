Objectives

My objective was to design and stand up a resilient two-node Proxmox VE cluster on HP ProDesk Mini systems, add a lightweight QDevice for quorum, provide a GNS3 network-simulation environment, build a Windows/Active Directory lab, and keep a Kali security workstation on a Windows Mini PC using VirtualBox for isolation.

Scope

Architecture

The design centers on a two-node Proxmox VE cluster that uses Corosync for membership and quorum, augmented by a Linux QDevice (corosync-qnetd) on a Windows Mini PC to provide a third vote. This enables correct quorum decisions in a two-node topology without adding a third hypervisor. pve01 is allocated to network simulation and Linux services, including GNS3 Server and general-purpose Linux VMs. pve02 is allocated to a Windows-based identity lab composed of a Windows Server domain controller and two Windows clients, plus an Ubuntu Desktop.

Primary VM disks remain on per-node local storage to keep the footprint simple and inexpensive for a small lab. Backups, configuration exports, and selected Proxmox backups target a portable 256 GB SSD, with explicit separation between transient snapshots and durable backups. The Kali security workstation remains in VirtualBox on the Windows Mini PC to keep intentionally vulnerable activities isolated from the cluster.

Why it was done: Hardware capabilities are to be confirmed and documented before installation, and hardware virtualization (Intel VT-x/VT-d) is to be enabled because Proxmox VE and nested GNS3 appliances depend on it.

What the technology is: Proxmox VE is a Debian-based virtualization platform that uses KVM for virtual machines and LXC for containers. GNS3 is a network simulation/orchestration platform that typically runs QEMU/KVM virtual appliances and Docker containers. Intel VT-x is the CPU hardware virtualization extension used by KVM to accelerate VMs, and Intel VT-d (IOMMU) enables DMA remapping and device passthrough.

How the technology works: KVM relies on Intel VT-x (with EPT) to virtualize privileged CPU operations with minimal overhead. How it was done: The intended procedure was to initialize the cluster on pve01, join pve02 to the cluster, validate Corosync ring communication and clock synchronization between nodes, and configure the cluster to use the Linux QDevice by pointing it at the corosync-qnetd service hosted on 192.x.x.13.

Why it was done: A two-node cluster can lose quorum when one node is unavailable, so a third vote is required to maintain quorum. The Linux QDevice supplies the third quorum vote to improve voting decisions. This does not by itself provide high availability; automatic VM recovery would also require suitable shared storage, a tested HA configuration, and enough capacity on the surviving node.

What the technology is: Proxmox VE clustering relies on Corosync for membership and quorum. In a two-node topology, a QDevice (quorum device) acts as an external arbitrator to provide an additional vote. The QDevice architecture consists of corosync-qnetd (the arbitrator service running on the external host/VM) and corosync-qdevice (the agent on each cluster node that communicates with qnetd). This arrangement lets a two-node cluster achieve an odd number of votes without adding a full third hypervisor node.

How the technology works: Corosync forms a membership ring and assigns votes to calculate quorum. With two nodes plus a QDevice, the cluster has three total votes; quorum requires a majority (2/3). If one node fails but both surviving endpoints (the remaining node and the QDevice) can still communicate, the cluster remains quorate. In a partition, the side that retains connectivity to qnetd and at least one node retains quorum. Time synchronization is important because Corosync’s token and membership algorithms assume stable clocks; poor time sync can cause spurious membership changes.

Dependencies: The QDevice VM was specified to run corosync-qnetd with approximately 512 MB RAM, use a static IP address at 192.x.x.13, auto-start when the Windows Mini PC boots, and remain available when the cluster needs its vote. It was explicitly scoped to provide quorum only (no workloads or shared storage).

Dependencies: Prerequisites include: both Proxmox nodes installed and reachable; stable network connectivity among pve01, pve02, and the QDevice host; consistent time synchronization on all three systems; static addressing and working name resolution for the Corosync ring and the QDevice endpoint; and firewall allowances for Corosync and qnetd traffic in the chosen transport/ports used by the environment.

Expected result: The cluster should report three quorum votes and remain quorate when either node is taken offline.

Technical significance: Adding a QDevice to a two-node Proxmox VE cluster enables correct quorum decisions with minimal additional infrastructure, reducing the risk of split-brain or write suspension when one node is offline. It decouples quorum from storage and compute design, allowing the lab to practice clustering semantics before introducing and validating full HA with shared storage.

RecommendationRestrict qnetd exposure to the two Proxmox nodes via host firewall and network ACLs; keep the QDevice VM and its Windows host patched and configured to avoid sleep/hibernation; avoid colocating the QDevice with untrusted or unstable workloads; protect any keys/certificates used by qnetd/qdevice; and monitor for unexpected access attempts to the QDevice service.

What the technology is: IEEE 802.1Q VLANs logically partition a single Layer 2 switch into multiple broadcast domains, allowing distinct security and routing policies per segment. Inter-VLAN routing, if required, is provided by a router or L3 firewall using subinterfaces (router-on-a-stick) or SVI equivalents. The switch management interface can be bound to a dedicated management VLAN to reduce exposure.

Lessons Learned

Upfront hardware validation matters: confirming VT-x/VT-d in firmware and documenting precise hardware details before installation reduces integration risk and accelerates troubleshooting later. Memory reliability is foundational; running a full memory test after upgrading to 32 GB per node helps prevent nondeterministic failures under KVM workloads.

Cluster hygiene begins with identity and parity: unique, DNS-resolved hostnames and static management IPs, combined with matching Proxmox versions, are prerequisites for a clean cluster join and predictable operations. In a two-node topology, a QDevice is the right tool to achieve an odd number of votes; it improves quorum decisions but does not deliver HA by itself.

Protection strategy must distinguish snapshots from backups. Snapshots are co-resident with the VM and are best used as short-lived safety nets before risky changes. Durable recovery depends on backups to a separate medium; keeping a portable SSD disconnected or otherwise protected when idle reduces exposure.

Recommendations

RecommendationStandardize both nodes on the same BIOS/UEFI version and virtualization settings; set a firmware admin password and disable unneeded boot devices or remote management features not required for the lab.
RecommendationAfter RAM installation, run multiple full passes of a memory test and capture evidence of zero errors; post-Proxmox, monitor kernel logs for MCE/EDAC events during initial load.
RecommendationVerify installer media integrity; reserve the chosen IPs and create forward and reverse DNS records before installation; confirm time synchronization on all systems prior to clustering.
RecommendationEncrypt the external SSD with LUKS, mount it by UUID at a dedicated path with restrictive options (e.g., noexec,nosuid,nodev), and set is_mountpoint=1 in storage.cfg to avoid writing to root if the device is absent.
RecommendationAlign backup schedules to periods when the SSD is attached; define prune/retention policies and enable job notifications; periodically validate restore to a scratch target.
RecommendationRestrict access to the Proxmox web UI and SSH on a management segment or via firewall rules; enable 2FA for root@pam and prefer SSH key-based authentication.
RecommendationFor the QDevice, ensure the Windows host does not sleep or hibernate the VM; restrict qnetd exposure to the two Proxmox nodes; monitor qnetd health and cluster quorum state, and document recovery procedures.

It establishes the prerequisites and configuration needed for a clean cluster build and clarifies that snapshots and quorum alone do not provide HA.
