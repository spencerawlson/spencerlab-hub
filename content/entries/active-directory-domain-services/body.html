Active Directory Domain Services

Building a minimal AD DS lab in VirtualBox: a static-IP Windows Server promoted to domain controller for adlab.com, DNS on the DC, and clients joined to the domain — with the DNS and time-sync warnings left open for follow-up.

Project Active Directory Domain ServicesGenerated 2026-09-08T10:19:52.272Z

Executive Summary

I built a minimal Active Directory Domain Services (AD DS) lab in Oracle VirtualBox to demonstrate end-to-end domain provisioning and client domain-join. I configured a Windows Server with a static IPv4 address (192.x.x.10/24), set its hostname to DC1, installed AD DS and DNS via Server Manager, and promoted it to a domain controller for a new forest and domain, adlab.com. I validated the deployment by inspecting AD DS role presence in Server Manager and Active Directory Users and Computers, observing computer objects (PC1, PC2) in the domain, and signing in to the ADLAB domain on the client. I also verified network settings on DC1 and performed basic name resolution checks. The lab achieves centralized authentication and directory services on a private virtual network, with minor unresolved observations highlighted for follow-up.

InferredThe nslookup output showing a DNS request timeout on ::1 followed by a valid A record for adlab.com, together with DNS Client and Time Service event log entries, suggests IPv6/DNS and time synchronization need refinement to eliminate intermittent resolution and Kerberos warnings.

Objectives

My objective was to set up a Windows domain and join a client to it. Success criteria were: a Windows Server configured as an AD DS domain controller with DNS for adlab.com; a Windows client on the same private network appearing in the domain and able to present an AD domain sign-in; and administrative visibility of domain objects using standard Microsoft MMC tools.

Scope

I configured a Windows Server VM as an AD DS domain controller with DNS, static IP addressing, server naming, and domain creation. I configured a Windows client VM on the same private virtual network and joined it to the new domain to validate connectivity and domain authentication paths. The work covers basic deployment and validation of an AD DS environment; advanced services and hardening were out of scope.

Requirements

The project record did not state explicit prerequisites or constraints.

Environment

I ran the lab in Oracle VirtualBox using a private virtual network. The Windows Server host (DC1) was configured with IPv4 address 192.x.x.10/24 and default gateway 192.x.x.1, and shows Primary DNS suffix adlab.com. Server Manager identifies the machine as DC1 joined to adlab.com, and the OS watermark indicates Windows Server 2025 Standard (build 26100). A Windows client VM (PC1) resided on the same network and presented AD domain sign-in for ADLAB; the client’s Settings view shows the device name PC1 and an account in the adlab.com domain.

Architecture

I implemented a single-domain AD architecture. One Windows Server VM provides both AD DS and DNS for adlab.com and uses local DNS resolution on the domain controller. One Windows client VM resides on the same private network and uses the domain controller for name resolution and domain authentication to access the ADLAB domain.

Methodology

I sequenced the build by first assigning a static IP configuration and applying a role-appropriate hostname, then installing AD DS and DNS via Server Manager. I used the AD DS configuration workflow to create a new forest and domain (adlab.com) and promote the server. I verified role installation and domain creation by inspecting Server Manager tiles and Tools, and by reviewing domain objects in Active Directory Users and Computers. I confirmed client integration by observing the PC1 computer object and the client’s ADLAB domain sign-in prompt; I further inspected ipconfig output on DC1 and executed an nslookup for adlab.com to sanity-check DNS resolution.

Implementation

I used the Server Manager Add Roles and Features wizard to install AD DS and DNS. Before promotion, I configured the Ethernet adapter on the server with a static IPv4 address and gateway and set the computer name to DC1. I then launched the “Promote this server to a domain controller” workflow, selected “Add a new forest,” set the domain name to adlab.com, and supplied the DSRM password. After promotion, I validated the presence of AD DS and DNS in Server Manager, opened Active Directory Users and Computers to confirm domain objects (including PC1 and PC2 in Computers), and observed domain sign-in prompts for ADLAB on the client. I captured ipconfig /all from DC1 to verify addressing and suffix configuration and ran nslookup adlab.com to confirm name resolution returned 192.x.x.10 despite an initial timeout over ::1. Event views showed AD-related warnings to be addressed later.

Step-by-Step Process

The following steps summarize the ordered build and verification activities and why each mattered for a functional AD DS domain with DNS-backed name resolution.

1. Install ADDS and DNS

On Server Manager, I clicked on Add roles and features. Chose DNS and Active Directory Domain Servers then install them

The Active Directory Domain Services (AD DS) and Domain Name System (DNS) server roles were installed on the Windows Server.

How it was done: Installation was performed via Server Manager using the Add Roles and Features wizard with DNS and Active Directory Domain Services selected and the installation executed to completion.

Actual result: Server Manager's Dashboard displays AD DS and DNS role tiles and the Tools menu lists Active Directory administration utilities, while the Active Directory Users and Computers view shows the adlab.com domain and a host named DC1, which together indicate the AD DS and DNS roles are present on the server.

2. Add Static IP, remove DHCP

To add a static IP Address and remove DHCP, On Server Manager, I clicked on Local Server then clicked the link next to Ethernet about IPv4. I, then, clicked on Network Connection, right-click on Properties and clicked on Internet Protocol v4 ...TCP/IPv4, clicked on Properties then add IP, Subnet Mask, Default Gateway and Preferred DNS.

The server's Ethernet interface was assigned IPv4 address 192.x.x.10 with subnet mask 255.x.x.0 and default gateway 192.x.x.1, and DHCP was disabled.

How it was done: The Server Manager GUI was used to open the Ethernet adapter properties and the Internet Protocol Version 4 (TCP/IPv4) settings, where the static IP, subnet mask, default gateway, and preferred DNS were entered.

Why it was done: A static IPv4 address and local DNS resolution were configured to provide a stable network identity and reliable name resolution, both of which are prerequisites for Active Directory Domain Services operation.

3. Change Computer Name

On Server Manager, I went to Local Server and clicked on the Computer/Server Name (in Properties). In System Properties, I clicked on Change...then changed the name into DC1

The computer name was changed to DC1 via System Properties (Change...).

Why it was done: Assigning a role-descriptive hostname (e.g., 'DC1') prior to or during Active Directory deployment aids administrative identification and aligns with common naming practices for domain controllers.

Actual result: System artifacts show the host name as 'DC1', the Primary DNS suffix as 'adlab.com', and an IPv4 address of 192.x.x.10.

4. Promote to Domain Controller and Creating a new domain

On Server Manager, I clicked the notification flag, clicked on promote this server to Domain Controller. In Active Directory Domain Services configuration, I created a new forest by clicking on Add a new forest. Typed in the Domain name "adlab.com" in Domain name field clicked next until I am asked to type in and confirm a password (DSRM: Directory Service Restore Mode) then install

The server was promoted to a Domain Controller and a new Active Directory forest and domain named "adlab.com" were created using the Active Directory Domain Services configuration wizard.

How it was done: The Server Manager notification flag was used to launch the 'Promote this server to a domain controller' workflow, the 'Add a new forest' option was selected, 'adlab.com' was entered as the domain name, and a Directory Services Restore Mode (DSRM) password was provided before installation.

Actual result: Active Directory objects for the adlab.com domain are present, including default containers and computer objects (PC1, PC2), and domain sign-in prompts for the ADLAB domain are visible, indicating successful promotion and domain creation.

Lessons Learned

Setting a static IP and ensuring the domain controller resolves names locally are non-negotiable prerequisites for AD DS stability. Validating with MMC tools (ADUC) and observing domain sign-in on the client provided fast, reliable checks that the core control plane was in place. The nslookup timeout over ::1 and event entries for DNS Client and Time Service emphasize that DNS and time coherence directly affect AD reliability and should be verified immediately after promotion to preempt Kerberos-related issues.

InferredThe ‘Server: UnKnown’ and timeout when querying via ::1 indicates reverse lookup naming for the DNS service and/or IPv6 DNS handling was not fully configured, even though the adlab.com A record resolved to 192.x.x.10.

Recommendations

RecommendationConfigure authoritative time on the domain controller (e.g., w32time with reliable NTP sources) and verify Event Viewer shows a healthy Microsoft-Windows-Time-Service state to avoid Kerberos ticket issues.
RecommendationReview DNS server interfaces and bindings; if IPv6 is required, ensure IPv6 DNS is fully configured with appropriate reverse zones. If IPv6 is not in scope, prefer 127.x.x.1 as the local resolver and disable IPv6 on the adapter to eliminate ::1 lookup anomalies in this lab context.
RecommendationCreate reverse lookup zones for the in-scope subnets so tools like nslookup can resolve the DNS server’s PTR and avoid ‘Server: UnKnown’ during diagnostics.
RecommendationDocument the client DNS settings to ensure all domain-joined clients point exclusively to the domain controller’s DNS and not to external resolvers on the lab network.

Conclusion

I deployed a single-domain AD DS environment on VirtualBox by configuring a Windows Server (DC1) with static IP, installing AD DS and DNS, and promoting it to the adlab.com domain. I observed the domain and its objects in Active Directory Users and Computers, saw PC1 and PC2 listed, and used the client’s ADLAB sign-in to exercise domain authentication on the lab network. Basic DNS resolution for adlab.com returned the domain controller’s address, with minor IPv6-related lookup behavior and timing warnings noted for follow-up. The lab demonstrates the core workflow for establishing centralized authentication and directory services on a private virtual network.
